# 「拾光集」前后端接口文档

> **面向**：后端开发、前后端联调、答辩演示
>
> **依据**：`frontend/src/api/*`（前端实际调用）、`frontend/src/mock/handlers.ts`（当前 mock 实现）、`docs/01-业务流程说明.md`、`docs/02-数据存储清单与业务对照.md`
>
> **状态**：前端已按本文档调用接口；当前默认 `VITE_USE_MOCK=true`，后端完成后把 `frontend/.env.development` 改为 `VITE_USE_MOCK=false` 即可切换。

---

## 1. 快速结论

- 统一前缀：`/api`，开发环境 Vite 把 `/api` 代理到 `http://localhost:8080`
- 统一响应：`{ code, message, data }`，`code = 0` 表示成功
- 鉴权：`Authorization: Bearer <token>`，登录后由前端自动附加
- 前端 API 层共定义 **55 个接口**（其中 `GET /wallet` 暂未调用，余额当前取自 `GET /auth/me`），覆盖 F1–F14
- 后端还缺 4 块主要能力：**图片上传、交付节点、卖家售后响应、定时任务**；此外还需要补一个置换完成接口（见 5.9、第 8 节）
- 当前前端列表接口按 **数组** 返回，不做分页；如果后端加分页，前端需要同步改 `ItemCard` 等列表页

## 2. 通用约定

### 2.1 请求与响应

所有接口均为 JSON：

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json
Authorization: Bearer <token>   # 需要登录的接口
```

成功响应：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

失败响应：

```json
{
  "code": 400,
  "message": "余额不足，请先充值"
}
```

前端在 `frontend/src/api/client.ts` 的响应拦截器中统一处理：

- `code === 0`：返回 `data`
- `code !== 0`：抛出 `Error(message)`，页面用 `ElMessage.error` 展示
- HTTP 非 2xx：读取 `error.response.data.message`

**建议后端实现**：业务错误统一返回 HTTP 200 + `code != 0`；未登录返回 HTTP 401 + `{ code: 401, message: "请先登录" }`。两者前端都能处理。

### 2.2 错误码

| code | 含义 | 典型场景 |
|---|---|---|
| 0 | 成功 | — |
| 400 | 参数错误 / 业务规则不满足 | 余额不足、状态不允许、重复评价 |
| 401 | 未登录 / token 失效 | 未携带 token、token 过期 |
| 403 | 无权限 | 学生访问运营接口、操作他人订单 |
| 404 | 资源不存在 | 物品、订单、悬赏、仲裁不存在 |
| 409 | 冲突（可选） | 物品已被锁定、用户名重复 |
| 500 | 服务端异常 | 未捕获异常 |

前端不会按 code 做特殊跳转，**后端必须自己校验角色和资源归属**，不能只依赖前端路由守卫。

### 2.3 身份与角色

| 角色 | 枚举值 | 能做什么 |
|---|---|---|
| 学生 | `student` | 注册、认证、发布、下单、求购、置换、售后、评价 |
| 运营 | `operator` | 物品审核、仲裁处理、运营报表 |
| 管理员 | `admin` | 学籍、分类、自提点、运营账号；也可访问运营工作台 |

请求头中的身份由后端从 JWT 解析，不信任前端传入的 `userId` / `role`。

### 2.4 命名、日期、金额

| 项 | 约定 |
|---|---|
| JSON 字段 | camelCase，如 `itemId`、`tradeStatus` |
| 数据库字段 | snake_case，如 `item_id`、`trade_status` |
| 日期时间 | ISO 8601 字符串，如 `2026-11-17T13:12:00+08:00`；前端用 dayjs 格式化 |
| 金额 | JSON number，后端用 `BigDecimal`，DB `DECIMAL(10,2)` |
| 物品编号 | number |
| 订单号 | string，如 `SO20261117001` |
| 枚举 | 传枚举 code（英文），不要传中文显示名 |

### 2.5 分页

当前前端**没有分页**，列表接口返回数组：

```json
{ "code": 0, "message": "ok", "data": [ ... ] }
```

`PageResult<T>` 类型已经预留但未使用。课程项目建议先保持数组；如果要做分页，至少需要同步改 `Search.vue`、`Orders.vue`、`ReviewList.vue` 等页面。

### 2.6 幂等与并发（后端必须做）

- 支付、放款、退款、扣回：同一 `(订单号, 类型, 账户标识)` 只能产生一条流水，数据库唯一键兜底
- 下单：同一物品只能存在一张有效订单，锁定物品用行锁或乐观锁
- 确认收货：重复请求只执行一次放款、信用、履历、通知
- 审核、仲裁裁定：重复提交返回“已处理”，不能重复写记录
- 加锁顺序固定：**物品 → 订单 → 用户 → 平台账户**，避免死锁

## 5. 接口清单（按模块）

### 5.1 认证模块 F1

**前端**：`frontend/src/api/auth.ts`，调用方 `frontend/src/stores/auth.ts`
**页面**：`/login`、`/register`
**建议后端**：`modules/auth/controller/AuthController.java`、`service/AuthService.java`、`dto/LoginRequest.java`、`dto/RegisterRequest.java`
**表**：`app_user`

#### POST `/auth/login`

- 功能：用户名 + 密码登录，返回 token 和当前用户
- 鉴权：公开
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 用户名 |
| password | string | 是 | 明文密码，后端校验哈希 |

- 响应：`LoginResult = { token: string, user: User }`
- 规则：
  - 用户不存在或密码错误统一返回“用户名或密码错误”
  - 封禁用户返回 403
  - token 建议 JWT，包含 `userId`、`role`
  - 前端把 token 存 `localStorage.sgj_token`，用户存 `sgj_user`

#### POST `/auth/register`

- 功能：注册学生账号
- 鉴权：公开
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| username | string | 是 | 3–20 字符，全局唯一 |
| password | string | 是 | 至少 6 位 |
| nickname | string | 是 | 昵称 |
| contact | string | 否 | 联系方式 |

- 响应：`LoginResult`
- 规则：
  - 注册后 `role=student`、`verifyStatus=unverified`、`creditScore=100`、`balance=0`
  - 不自动绑定学号，学号在 F2 认证时绑定
  - 用户名唯一由数据库唯一约束兜底
  - 建议注册后直接返回 token，前端注册成功会进入认证页

#### GET `/auth/me`

- 功能：获取当前登录用户，用于刷新页面后恢复状态、刷新余额/信用
- 鉴权：登录
- 响应：`User`

#### POST `/auth/logout`

- 功能：退出登录
- 鉴权：登录
- 响应：`null`
- 说明：如果使用无状态 JWT，后端可以只返回成功；如果要让 token 立即失效，需要引入黑名单或短期 token

### 5.2 学籍认证模块 F2

**前端**：`frontend/src/api/user.ts` 的 `userApi.verify`
**页面**：`/verify`
**建议后端**：`modules/verification/controller/VerificationController.java`、`service/VerificationService.java`
**表**：`student_roster`、`app_user`、`verification_record`、`notification`

#### POST `/verification`

- 功能：提交学籍信息，与学籍表比对，通过后绑定学号并开放交易资格
- 鉴权：登录
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| studentNo | string | 是 | 学号 |
| name | string | 是 | 姓名 |
| college | string | 是 | 学院 |
| major | string | 是 | 专业 |
| grade | string | 是 | 年级 |

- 响应：更新后的 `User`
- 必做规则：
  - 按 `studentNo` 查 `student_roster`，比对姓名与学院
  - 一个学号只能绑定一个账号（`app_user.student_no` 唯一）
  - 每次提交生成一条 `verification_record`（结果、申请时间、核验时间），不覆盖历史
  - 通过：写 `user.verify_status=verified`、绑定学号，写通知
  - 失败：写 `verification_record`（驳回），`user.verify_status=rejected`，可重新提交
  - 未登录返回 401；已认证用户重复提交返回 400
- 前端演示数据：`20230001 / 林小满 / 计算机学院 / 软件工程 / 2023`

  - 订单转 `pending_delivery`，物品保持 `locked`
  - 幂等：重复支付返回已支付/当前订单状态，不能重复扣款

- 功能：买家取消未支付订单
- 鉴权：登录，且为买家
- 响应：`Order`
- 规则：仅 `pending_payment` 可取消；订单 `cancelled`，物品回 `on_sale`，不写支付流水

- 功能：买家确认收货，完成交易并放款
- 鉴权：登录，且为买家
- 响应：`Order`（`tradeStatus = completed`）
- 必做规则：
  - 仅 `pending_confirm` 可确认；超时由定时任务自动确认
  - 订单 `completed`、物品 `completed`，物品当前持有人改为买家
  - 平台托管 −，卖家余额 +
  - 写两条流水：平台 `payout`、卖家用户 `payout`
  - 写履历“成交”：新主人、寄语；写信用流水双方 +2 并同步 `user.credit_score`
  - 写通知“订单完成”给双方
  - 若订单有 `bountyId`，悬赏单置 `matched`
  - 幂等：重复确认不得重复放款/加信用

- 功能：评价订单（买卖双方各一次）
- 鉴权：登录，且为订单参与方
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| rating | number | 是 | 1–5 |
| tags | string[] | 否 | 标签 |
| content | string | 否 | 内容 |

- 响应：`Review`
- 规则：
  - 仅 `completed` 订单可评价
  - `review` 表 `(order_no, reviewer_id)` 唯一，一单一评
  - 评价状态 `valid`；评价不改履历和信用
  - 超时未评价由定时任务写 `system` 默认评价（不计分）

#### POST `/orders/{id}/aftersale`

- 功能：买家申请售后
- 鉴权：登录，且为买家
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| reason | string | 是 | 退款原因 |
| evidence | string | 否 | 举证说明 |

- 响应：更新后的 `Order`
- 分支规则（按文档 F8）：
  - `pending_delivery`（未发货）：直接退款，托管退回买家，订单售后 `refunded`，物品回 `on_sale`
  - `pending_confirm` / `completed`：进入 `refunding`，卖家需在 **2 分钟**内响应；同意则退款，拒绝转仲裁
  - `completed`：仅收货后 **5 分钟**内可申请
  - `pending_payment`、`cancelled`、已有售后中的订单不可申请
  - 退款/扣回/回滚必须写支付流水、信用流水、履历、通知
- **当前 mock 简化**：已发货/已完成的售后直接转 `arbitrating`；后端应按文档实现卖家 2 分钟响应（见 8.2）

  - 履历“建档”由物品业务写入，审核不要在 F12 重复写两张主表（实现上可调用 ItemService 统一完成）

#### GET `/ops/arbitrations`

- 鉴权：运营 / 管理员
- 响应：`Arbitration[]`，待处理优先

#### POST `/ops/arbitrations/{id}/resolve`

- 鉴权：运营 / 管理员
- 请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| result | string | 是 | `buyer` / `seller` |
| note | string | 否 | 裁定说明 |

- 响应：`Arbitration`
- 规则：
  - 仅 `pending` 可裁定
  - 支持买家：退款/扣回、订单售后 `refunded`、物品回 `on_sale`、归还卖方、履历“退货”、评价作废、信用回滚
  - 支持卖家：订单售后 `none`，交易状态保持原值
  - 写仲裁结果、处理人、处理时间、通知双方
  - 资金操作必须走 `LedgerService`

#### GET `/ops/report`

- 鉴权：运营 / 管理员
- 响应：`ReportData`
- 统计口径（F13）：
  - 成交量/成交额：`completed` 订单
  - 退款率：`退款订单数 + 扣回订单数 / 支付订单数`；按 `account_type=user` 的支付流水、订单号去重
  - 品类分布：按物品分类
  - 接力/流转：履历事件 `成交/置换`
  - 悬赏、置换：悬赏单/方案状态
  - 学院维度：学籍表 + 用户学号；运营/管理员无学号，排除
  - **实时计算，不落报表表**

建议按业务域分包，每个模块内 `controller / service / mapper / entity / dto / enums`：

```
backend/src/main/java/com/shiguangji/
├── common/                  Result、异常、JWT、配置、文件存储
├── modules/
│  ├── auth/                 F1
│  ├── verification/         F2
│  ├── user/                 用户、信用、钱包
│  ├── catalog/              学籍、分类、自提点
│  ├── item/                 F3、F4、F10

│  ├── payment/              托管、流水、平台账户
│  ├── aftersale/            F8
│  ├── bounty/               F9
│  ├── exchange/             F11
│  ├── moderation/           F12
│  ├── report/               F13
│  ├── admin/                F14

└── scheduler/               定时任务
```

### 6.1 模块依赖

- `payment` 是交易域公共底座，先实现 `LedgerService`（充值/支付/放款/退款/扣回、双流水、余额快照、幂等）
- `notification` 是公共能力，各模块只调用 `NotificationService`
- `catalog` 提供分类、自提点、学籍只读查询，其他模块不要直接查它的 mapper
- `trade` 依赖 `item`（锁定/完成/变更持有人）、`payment`、`notification`、`user`（信用）
- `aftersale` 依赖 `trade`、`payment`、`item`、`moderation`
- `exchange` 依赖 `item`、`trade`、`notification`
- `report` 只读所有模块

### 6.2 建议分工

| 方向 | 负责模块 | 对应业务 | 主要表 |
|---|---|---|---|
| A. 账号与基础域 | auth、verification、user、catalog、admin、notification | F1、F2、F14 | app_user、student_roster、verification_record、category、pickup_point、notification |
| B. 物品与交易域 | item、trade、payment、aftersale、scheduler | F3–F8、F10 | item、item_image、item_history、trade_order、payment_record、platform_account、delivery_record、review、credit_record、arbitration |
| C. 扩展与运营域 | bounty、exchange、moderation、report | F9、F11–F13 | bounty、exchange_intent、exchange_plan、audit_record、arbitration |

### 6.3 建议开发顺序

1. `common`：`Result`、`ErrorCode`、全局异常、JWT、`@RequireVerified`、分页/时间/金额工具
2. `auth` + `user` + `catalog` + `admin` 基础数据
3. `item` 列表/详情/发布/审核
4. `payment` + `trade` 下单/支付/取消/确认
5. `notification` + `aftersale` + 运营仲裁
6. `bounty` + `exchange` + `report`

## 7. 状态机与关键约束

### 7.1 物品状态

```
待审核 pending → 在售 on_sale → 已锁定 locked → 已完成 completed
        ↓驳回 rejected        ↑取消/退款解锁        ↑再次上架 → pending
        ↓下架 off_shelf / 冻结 frozen
```

- 物品编号终身不变；F10 复用原编号
- “已锁定”覆盖待支付到待确认的购买，以及置换占用
- 订单状态与物品状态分离；物品表只回答“现在能不能卖”

### 7.2 订单双状态

- `tradeStatus`：待支付 → 待交付 → 待确认 → 已完成；取消为旁支
- `afterSaleStatus`：无 → 退款中 → 仲裁中 → 已退款
- 售后变化不改交易状态；仲裁驳回时售后恢复 `none`
- 订单的买家/卖家/金额是快照，物品的当前持有人是现值

### 7.3 资金

- 托管闭环：买家余额 → 平台托管 → 卖家余额
- 未完成退款回托管来源；已完成售后从卖家余额扣回
- 余额不足可记负余额并限制发布（但支付时必须有足够余额）
- 每笔变动两条流水（用户/平台），带余额快照；外部单号唯一
- 充值：`order_no` 为空、账户类型=用户、账户标识=用户号、不进托管

### 7.4 时限（全部可配置）

| 业务 | 文档时限 | mock 演示 |
|---|---|---|
| 未支付取消 | 30 秒 | 2 分钟 |
| 自动确认收货 | 10 分钟 | 未实现 |
| 评价窗口 | 10 分钟 | 不限制 |
| 收货后售后窗口 | 5 分钟 | 5 分钟 |
| 卖家售后响应 | 2 分钟 | 直接转仲裁 |
| 置换确认 | 10 分钟 | 前端倒计时，后端未实现 |

后端统一读 `app.timeout.*`，测试环境可改秒级。
