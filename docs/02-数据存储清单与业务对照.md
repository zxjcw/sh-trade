> **用途**：按"表"为单位梳理整个项目的数据存储，并说明每条业务读到/写到哪些表，作为可行性研究阶段的数据基础、后续第 3 章数据库设计的依据。
> **口径**：物理上只有 **1 个数据库、21 张表**；本文逐表列出，不再做"分组"。

## 二、设计要点（19 条）

### 一、身份与权限

1. **角色三分，各管一摊**：学生买卖一体；运营负责物品审核、仲裁与报表；管理员负责学籍数据、分类、自提点等基础数据。运营不改学籍，管理员不判交易——数据主权与业务处置权分开。
2. **账号与认证分离**：用户名是唯一登录账号，学号在认证通过后才绑定；一个学号只能绑定一个账号；每次认证生成一条新记录（申请/核验时间、结果），不覆盖历史，认证通过才获得交易资格。

### 二、标识与状态

3. **一物一码，履历随编号**：物品编号终身不变；F3 首次发布生成新编号，F10 再次上架复用原编号。编号不变，履历才能连续，“第 N 任主人”才有意义。
4. **物品状态单一主链**：`待审核 → 在售 → 已锁定 → 已完成`；驳回回待审核、取消回在售，冻结与下架为旁支。“已锁定”覆盖购买（待支付到待确认）与置换占用，不设“交易中”，物品表只回答“能不能卖”。
5. **订单双状态**：`交易状态`（待支付/待交付/待确认/已完成/已取消）与 `售后状态`（无/退款中/仲裁中/已退款）分离。售后变化不改交易状态；仲裁驳回时售后恢复“无”，交易状态保持原值。
6. **状态只由业务推进**：普通订单的交易状态由 F5（建单、支付）与 F6（交付、确认）推进，置换单的交易状态由 F11 推进；F7 只评价，不写状态；支付记录、交付记录只记事件与时间，不反向触发订单状态变化。
7. **订单是快照，物品是现值**：订单表的买家、卖家、物品、金额是成交时的历史快照；物品表的“当前持有人”回答“现在在谁手里”。两者不能互相替代，查询时各取所需。

### 三、数据一致性

8. **当前值与流水分离**：用户表存当前信用分、认证状态、余额；信用记录表与支付记录表存“怎么变过来的”。任何当前值都必须能由流水推出。
9. **审核分工**：审核环节由 F3 写“结果”（物品状态、履历建档），F12 只写“记录”（审核人、结论、理由）；审核结果通知统一由 F12 写。仲裁执行所需的退款/回滚不受此限。
10. **一物一评**：评价以 `(订单号, 评价人)` 唯一，提交后不可改；评价状态区分有效、作废、系统默认；评价只影响展示与排序，不改履历与信用。
11. **结构约束必须落到库上**：用户名、学号、评价 `(订单号,评价人)`、收藏 `(用户号,物品编号)`、支付外部单号、支付 `(订单号,类型,账户标识)`、信用 `(用户号,关联订单号,原因)`、分类 `(父分类号,分类名)`、一级分类名、取件码、有效置换意向均加唯一约束；分类最多两级，每件物品仅一张**有效**首图（历史图不参与首图唯一）。

### 四、资金

12. **托管闭环**：买家余额 → 平台托管 → 卖家余额。未完成退款回托管来源，售后从卖家余额扣回；余额不足记负余额并限制发布，不允许“凭空退款”。
13. **流水、幂等与对账**：支付记录按账户逐笔记流水（账户类型=用户/平台，账户标识=用户号/平台账户号），只写成功流水、只增不改，每笔带对应账户余额快照，外部单号唯一；退款/扣回用新流水冲抵。同一订单同一类型同一账户只允许一条流水，一人一单只加一次信用；充值流水订单号为空、账户类型=用户、账户标识=用户号，只加用户余额、不进平台托管；用户余额 = 充值 + 退款 + 放款 − 支付 − 扣回；平台托管余额 = 平台流入 − 平台流出，定时对账。
14. **售后资金分级**：未发货直接退（托管退回）；已发货需卖家同意或仲裁；已完成售后从卖家余额扣回，并回滚履历、信用与评价。三条路径的退款来源不同，不能混用。

### 五、履约与信任

15. **交付只做面交与自提**：不接快递。交付记录用时间戳表达进度——面交填约定时间/地点/核验时间，自提填入库/出库/取件码/自提点号——不另设状态字段，避免与订单状态重复。
16. **履历只由系统写**：建档、成交、置换、退货、维修五类事件由系统写入；用户只能追加维修/附件并标注来源；“寄语”由卖家在成交时填写，系统代写。
17. **通知只发“结果/行动”类**：认证结果、审核结果、悬赏命中、置换邀请、售后结果、仲裁受理、仲裁结果、订单完成；订单进行中的状态变化不发通知，在“我的订单”里看。
18. **时限统一为可配置的模拟时间**：30 秒未支付取消、10 分钟未确认自动确认、10 分钟评价窗口、5 分钟售后窗口（卖家自申请起 2 分钟内响应）、置换方案 10 分钟内确认。测试取分钟级，部署时改配置即可恢复真实值。
19. **统一记账口径：账户标识**：平台账户表是托管池（单行），不是用户表里的账号，因此支付记录的 `用户号` 不能填平台账户。为此支付记录增加 `账户标识`：用户流水填用户号，平台流水填平台账户表的账户号，`用户号` 只在用户流水填写。这样一笔支付、放款或退款产生的两条流水都能定位到唯一账户，`(订单号, 类型, 账户标识)` 唯一约束才有意义，平台流水也不再依赖 NULL 去重；每笔流水的“余额快照”对应各自账户（用户余额或托管余额），平台侧流水汇总后可与平台账户余额对账。

| 置换意向表 | 我的物品编号（状态=有效时） | 同一物品只有一条有效意向（MySQL 无部分索引，用生成列或应用层保证） |

### 建表顺序建议

```

  → 物品表、物品图片表、履历记录表
  → 悬赏单表、置换意向表、置换方案表
  → 订单表
  → 支付记录表、交付记录表、评价表、信用记录表、审核记录表、仲裁申请表、通知表、收藏表
```
